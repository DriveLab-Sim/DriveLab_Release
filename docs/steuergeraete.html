Steuergeräte (SDK)

Ein Steuergerät ist eine eigene Bibliothek (.dll), die du außerhalb von DriveLab baust. DriveLab lädt sie zur Laufzeit, hängt sie an einen oder mehrere virtuelle CAN-Busse und ruft sie in ihrem Takt auf – DriveLab selbst wird nie neu übersetzt.

Überblick

Dein Steuergerät sieht vom Bus nur benannte Signale in physikalischen Einheiten – DriverInputs.AcceleratorPedal in Prozent, nicht Byte 0. Packen und Entpacken übernimmt DriveLab anhand der DBC.

Das SDK liegt im Installationsordner unter sdk:

OrdnerInhalt
include/die Schnittstelle: drivelab_ecu.h (C) und drivelab_ecu.hpp (C++)
src/drivelab_ecu_runtime.c – wird automatisch mitgebaut
cmake/CMake-Paket mit drivelab_add_ecu()
templates/ecu-project/Vorlage für drivelab ecu new
examples/die zwei Steuergeräte der Projektvorlage, in C++ und C

Voraussetzungen

  • CMake 3.21 oder neuer
  • ein 64-Bit-Compiler: MinGW-w64 (z. B. WinLibs oder MSYS2) oder Visual Studio 2022
  • optional die GNU Arm Embedded Toolchain für die Target-Gegenprobe
Installation per winget winget install Kitware.CMake und winget install BrechtSanders.WinLibs.POSIX.UCRT. Das WinLibs-Paket ist groß und lädt lange. Danach ein neues Terminal öffnen, sonst fehlen die Programme im PATH.

Schnellstart

Du tauschst im Standardprojekt das Powertrain-Steuergerät gegen ein eigenes aus.

1 · Projekt anlegen und das Netz ansehen

Eingabeaufforderung
drivelab new MeinProjekt
drivelab ecu list MeinProjekt

Das Standardprojekt bringt zwei Steuergeräte mit: Powertrain macht aus der Pedalstellung eine Momentenanforderung und begrenzt die Motordrehzahl, Motor setzt die Anforderung ans Fahrzeug um.

2 · Eigenes Steuergerät anlegen und bauen

Eingabeaufforderung
drivelab ecu new PedalMap
cd %USERPROFILE%\Documents\DriveLab\ecus\PedalMap
cmake --preset mingw
cmake --build --preset mingw

Mit Visual Studio statt MinGW: --preset msvc. Heraus kommt build/mingw/pedal_map.dll.

3 · Prüfen, was in der Bibliothek steckt

Eingabeaufforderung
drivelab ecu check build/mingw/pedal_map.dll

4 · Ins Fahrzeug einhängen

pedal_map.dll nach projects/MeinProjekt/data/vECU/EE1/bin/ kopieren. In der network.json daneben beim Eintrag Powertrain Name und Bibliothek ändern; Takt und Versatz bleiben:

JSON
{
  "name": "PedalMap",
  "type": "native",
  "period_ms": 10,
  "offset_ms": 1,
  "params": { "library": "./bin/pedal_map", "gain": 1.5 }
}
Ersetzen, nicht ergänzen PedalMap sendet wie Powertrain die Botschaft TorqueRequest. Zwei Sender für eine Botschaft lehnt DriveLab ab.

5 · Laufen lassen

Eingabeaufforderung
drivelab validate MeinProjekt
drivelab run MeinProjekt

In can.tsv folgt TorqueRequest.RequestedTorque jetzt direkt dem Pedal (× 1,5), ohne Rampe und Drehzahlbegrenzung. Ab hier ist die Schleife immer gleich: Quelltext ändern, bauen, DLL kopieren, drivelab run. Nur Parameter aus der network.json zu ändern braucht keinen Neubau.

Aufbau eines Steuergeräts

So sieht das Steuergerät aus, das drivelab ecu new anlegt (gekürzt, clampf ist eine kleine Hilfsfunktion oben in der Datei):

C++
#include "drivelab_ecu.hpp"

class PedalMap : public drivelab::Ecu
{
public:
    dl_status create(drivelab::Context& ctx) override
    {
        pedal_ = ctx.input("DriverInputs.AcceleratorPedal");
        torqueRequest_ = ctx.output("TorqueRequest.RequestedTorque");

        if (!pedal_ || !torqueRequest_) {
            return DL_ERROR_SIGNAL;
        }

        gain_ = ctx.param("gain", 1.5f);
        timeout_ = ctx.param("timeout", 0.05f);

        return DL_OK;
    }

    void reset(drivelab::Context&) override
    {
        torque_ = 0.0f;
    }

    void step(drivelab::Context& ctx, float t, float dt) override
    {
        if (!ctx.isFresh(pedal_, timeout_)) {
            ctx.write(torqueRequest_, 0.0f);
            ctx.fault(0x0001, DL_SEVERITY_WARNING);
            return;
        }

        torque_ = clampf(ctx.read(pedal_), 0.0f, 100.0f) * gain_;
        ctx.write(torqueRequest_, torque_);
    }

private:
    drivelab::Signal pedal_;
    drivelab::Signal torqueRequest_;
    float gain_ = 1.5f;
    float timeout_ = 0.05f;
    float torque_ = 0.0f;
};

DRIVELAB_ECU(PedalMap, "PedalMap");
TeilWannAufgabe
createeinmal beim AufbauSignalnamen auflösen, Parameter lesen – nur hier sind Strings erlaubt. Alles außer DL_OK bricht den Aufbau mit einer Meldung ab, die das Signal beim Namen nennt.
resetvor jedem Laufalle internen Zustände zurücksetzen, sonst startet der zweite Lauf mit den Werten vom Ende des ersten
stepjeden Zyklusder zyklische Task. dt ist die eigene Zykluszeit aus der network.json, nicht der Simulationsschritt.
onFrameoptionalsieht jeden Rohframe auf seinen Bussen – für Diagnose oder Gateways; frame.bus sagt, auf welchem
DRIVELAB_ECU(Klasse, "Name")einmal je Bibliothekerzeugt alles, was DriveLab zum Laden braucht; am Dateiende

Signale, Parameter, Fehlerspeicher

Signale

Signale heißen Botschaft.Signal, wie in der DBC. Bei mehreren Bussen gibt Bus.Botschaft.Signal den Bus an, siehe Mehrere Busse.

  • output meldet an, dass dieses Steuergerät die ganze Botschaft sendet. Jede Botschaft hat genau einen Sender.
  • Gibt es das Signal nicht, ist der Handle ungültig (!in ist wahr). Ob das ein Fehler ist, entscheidest du.
  • read und write arbeiten in physikalischen Einheiten als float. Werte außerhalb des DBC-Bereichs werden auf die Grenze gesetzt.
  • isFresh(signal, maxAlter) und age(signal) sagen, wann das Signal zuletzt ankam. Ein nie empfangenes Signal ist nicht frisch und liest sich als 0.

Parameter

Alles unter params in der network.json kommt beim Steuergerät an:

C++
float   gain    = ctx.param("gain", 1.5f);        // Zahl
int32_t mode    = ctx.param("mode", int32_t{0});  // ganze Zahl
bool    enabled = ctx.param("enabled", true);     // Wahrheitswert

float    map[16];
uint32_t n = ctx.paramArray("kennlinie", map, 16);   // Zahlenliste

Fehlt ein Parameter, gilt der Vorgabewert. library und ecu sind reserviert.

Fehlerspeicher

C++
ctx.fault(0x0101, DL_SEVERITY_WARNING, "Pedal fehlt");

Wie in einem echten Steuergerät gibt es einen Eintrag je Code, mit Zähler sowie erstem und letztem Auftreten. Beim ersten Auftreten steht eine Zeile im Log, am Ende liegt der Speicher als ecu_faults.tsv im Laufordner. Stufen: DL_SEVERITY_INFO, _WARNING, _ERROR; der Lauf bricht bei keiner ab.

Zeitverhalten

Jedes Steuergerät läuft mit period_ms und optional offset_ms, beides Vielfache des Grundtakts base_dt_ms. Eine Botschaft, die in einem Takt gesendet wird, kommt im nächsten Grundtakt an. Das bildet die Übertragung ab und macht das Ergebnis unabhängig von der Reihenfolge in der network.json.

Mit dem Versatz legst du eine Kette so, dass jedes Steuergerät rechnet, kurz nachdem seine Eingänge angekommen sind:

0 ms · Fahrzeugsendet Pedal und Fahrzustand
→
1 ms · Powertrainliest sie, sendet TorqueRequest
→
2 ms · Motorliest sie, sendet ActuatorCommand
→
10 ms · Fahrzeugübernimmt den Stellbefehl

Ohne Versatz – alle bei 0 ms – wäre dieselbe Kette 20 ms statt 10 ms unterwegs. drivelab inspect vehicle rechnet diese Laufzeiten für jede Wirkkette aus.

Die network.json

Sie beschreibt das Netz eines Fahrzeugs und hängt in der Fahrzeugdatei unter components.ecus, relativ zu dieser.

  "dbc": "./EE1.dbc",

  "messages": {
    "DriverInputs": 10
  },

  "plant": {
    "period_ms": 10,

      "DriverInputs.AcceleratorPedal": { "quantity": "driver:throttle", "scale": 100.0 },

Mehrere Busse

Hat das Fahrzeug mehrere CAN-Busse, bekommt jeder einen Namen und seine eigene DBC. dbc, messages, trace_file und bitrate_kbps stehen dann je Bus unter buses statt oben:

JSON
{
  "base_dt_ms": 1,

  "buses": {
    "PER": { "dbc": "./PER.dbc", "bitrate_kbps": 1000,
             "messages": { "DriverInputs": 10, "TorqueRequest": 10 } },
    "INV": { "dbc": "./INV.dbc",
             "messages": { "InvSetpoint": 5 } }
  },

  "plant": {
    "period_ms": 5,
    "publish": {
      "DriverInputs.AcceleratorPedal": { "quantity": "driver:throttle", "scale": 100.0 },
      "INV.InvActual.Speed":           "vx"
    },
    "subscribe": { "throttle": "PER.ActuatorCommand.ThrottleCommand" }
  },

  "ecus": [
    { "name": "Powertrain", "type": "native", "period_ms": 10, "buses": ["PER"],
      "params": { "library": "./bin/powertrain_ecu" } },
    { "name": "Gateway", "type": "native", "period_ms": 5, "buses": ["PER", "INV"],
      "params": { "library": "./bin/gateway_ecu" } }
  ]
}
EintragBedeutung
buses.<Name>.dbcBusbeschreibung, Pflicht. Name aus Buchstaben, Ziffern, _ und -.
buses.<Name>.messagesZykluszeiten wie oben, nur für diesen Bus
buses.<Name>.trace_fileMitschnitt, Vorgabe can_<Name>.tsv
buses.<Name>.bitrate_kbpsVorgabe 500; nur für die Buslast im Report
ecus[].busesan welchen Bussen das Steuergerät hängt, Vorgabe alle. Die Reihenfolge ist der Index in frame.bus.

Namen

  • Bus.Botschaft.Signal wählt den Bus. Botschaft.Signal reicht, solange der Name auf den Bussen des Steuergeräts nur einmal vorkommt – sonst bricht der Aufbau mit „mehrdeutig“ ab und nennt die Busse.
  • Ein Steuergerät sieht nur die Signale und Frames seiner Busse. Das Fahrzeug hängt an allen.
  • Dieselbe ID auf zwei Bussen ist kein Konflikt: Botschaften gehören je Bus einem Sender.
  • Extended IDs (29 bit) aus der DBC werden erkannt; ecu list, Report und Mitschnitt schreiben sie als 0x0CFF0180x.

Rohframes und Gateways

ctx.bus("INV") (C: dl_bus(ctx, "INV")) liefert den Index für frame.bus, -1, wenn der Bus nicht angeschlossen ist. Ankommende Frames tragen denselben Index. Hängt das Steuergerät an nur einem Bus, wird frame.bus ignoriert.

C++
dl_status create(drivelab::Context& ctx) override
{
    per_ = ctx.bus("PER");
    inv_ = ctx.bus("INV");
    return per_ < 0 || inv_ < 0 ? DL_ERROR : DL_OK;
}

void onFrame(drivelab::Context& ctx, const dl_frame& frame, float t) override
{
    if (frame.bus != inv_ || frame.id != 0x283) { return; }

    dl_frame copy = frame;
    copy.bus = static_cast<uint8_t>(per_);    // weiterleiten
    ctx.sendFrame(copy);
}

Die Form mit dbc oben ist ein einzelner Bus ohne Namen und verhält sich wie bisher: can.tsv, Namen ohne Bus, buses an Steuergeräten nicht erlaubt.

Moment je Rad

Steuert eine VCU die Motoren einzeln, abonniert das Fahrzeug das Moment je Rad statt des Gaspedals:

JSON
"subscribe": {
  "torque_FL": "LOG.VCUsPP_Output.VCUsPP_TorqueFL_TORQUExREQ",
  "torque_RL": { "signal": "INV.INVRL_Motor_MEASUREMENTS.INVRL_Motor_TORQUExACT", "scale": 0.098 }
}
  • Gemeint ist das Moment an der Motorwelle in Nm. Das Antriebsmodell begrenzt es auf seine Kennlinie (Strom, Spannung, Drehzahl) und, mit Akku, auf dessen Leistungsgrenze.
  • Im Einspurmodell gilt die Summe beider Räder einer Achse.
  • Negative Momente (Rekuperation) setzt nur PmsmDrive um, die einfachen Motormodelle begrenzen auf null.

Log abspielen

Ein Steuergerät vom Typ replay legt Spalten aus einer CSV-Datei als Signale auf den Bus, z. B. die Momentanforderungen der echten VCU aus einem Fahrzeuglog. So lässt sich das Fahrzeugmodell mit derselben Ansteuerung fahren wie das Auto, ohne die VCU selbst einzubinden.

JSON
{ "name": "VCU_Log", "type": "replay", "period_ms": 5, "buses": ["LOG", "PER"],
  "params": {
    "file": "../../logs/accel.csv",
    "time_column": "Time", "time_unit": "ms", "shift_s": -1.01,
    "signals": {
      "LOG.VCUsPP_Output.VCUsPP_TorqueFL_TORQUExREQ": "VCUsPP_TorqueFL_TORQUExREQ",
      "PER.SCB_Throttle.SCB_Throttle_POS": { "column": "CIF_Throttle_POS", "scale": 1.0 }
    } } }
EintragBedeutung
fileCSV mit Kopfzeile, relativ zur network.json. Komma als Trenner, Namen dürfen in Anführungszeichen stehen.
time_column · time_unitZeitspalte, Vorgabe Time · s oder ms, Vorgabe s
shift_sDie erste Zeile ist 0, dazu kommt shift_s. -1.01 heißt: Sekunde 1,01 im Log ist der Start der Simulation.
signalsBussignal → Spalte, oder { "column", "scale", "offset" }; Wert = Spalte × scale + offset
  • Zwischen zwei Zeilen hält es den letzten Wert. Leere Zellen und Text wie undefined überspringt es – so passen Exporte, in denen jedes Signal nur in seinem eigenen Takt steht (Grafana).
  • Vor dem ersten Wert sendet es nichts, nach dem Ende des Logs bleibt der letzte Wert stehen.
  • Die Botschaften gehen im Takt aus messages, sonst mit period_ms.
  • Startet das Log in Fahrt, die Simulation mit derselben Geschwindigkeit starten (sim.v0) und shift_s passend wählen. Aus dem Stand ist das Reifenmodell beim Anfahren noch zu ungenau.

Bauen

Die CMakeLists.txt von drivelab ecu new ist im Kern:

CMake
find_package(DriveLabSDK REQUIRED)
drivelab_add_ecu(pedal_map src/PedalMap.cpp)

drivelab_add_ecu setzt alles, was ein Steuergerät braucht: keine Exceptions, kein RTTI, Compiler-Laufzeit fest hineingelinkt, nur der Einsprung exportiert. Den Pfad zum SDK hat ecu new in die CMakePresets.json geschrieben. Ohne Presets:

Eingabeaufforderung
cmake -B build -DDriveLabSDK_ROOT=%LOCALAPPDATA%/Programs/DriveLab/sdk
cmake --build build

Mehrere Steuergeräte sind mehrere Aufrufe. Mit DEPLOY_DIR landet die Bibliothek nach jedem Bauen direkt im Projekt:

CMake
drivelab_add_ecu(pedal_map src/PedalMap.cpp
    DEPLOY_DIR "C:/Users/.../Documents/DriveLab/projects/MeinProjekt/data/vECU/EE1/bin")

Regeln für Steuergeräte-Code

Derselbe Quelltext soll später auch auf einem Mikrocontroller laufen. Deshalb gilt im Steuergerät:

  • keine Exceptions, kein RTTI – schaltet drivelab_add_ecu ab
  • kein Heap: kein new, malloc, std::vector, std::string, std::map. Feste Arrays als Klassenmitglieder gehen.
  • float statt double – ein STM32 rechnet double in Software

Target-Gegenprobe

Eingabeaufforderung
cmake --preset mingw -DDRIVELAB_ECU_CHECK_TARGET=ON
cmake --build --preset mingw

Mit der GNU Arm Embedded Toolchain im PATH wird das Steuergerät bei jedem Bauen zusätzlich für einen Cortex-M4 übersetzt. Es entsteht nichts Lauffähiges – der Build bricht nur ab, sobald etwas im Code steht, das auf einem Mikrocontroller nicht geht.

In C statt C++

drivelab_ecu.hpp ist ein Komfort-Aufsatz; die eigentliche Schnittstelle ist reines C in drivelab_ecu.h. Ein vollständiges Beispiel: sdk/examples/MotorEcu.c.

Grenzen dieser Version

  • Ein Absturz im Steuergerät beendet DriveLab – die Bibliothek läuft im selben Prozess.
  • Am Fahrzeug kommen Gas, Bremse, Lenkung und das Antriebsmoment je Rad an; Bremsdruck je Rad geht noch nicht.
  • Das Motormodell kennt noch keinen Überlastschutz (I²t) und kein Verlustkennfeld.
  • Nur CAN. Die Busse sind ideal: jede Botschaft kommt einen Grundtakt später an, ohne Arbitrierung oder Verzögerung durch Buslast.
  • Pfade mit Zeichen außerhalb der Windows-Codepage werden nicht überall unterstützt.
  • Das Preset msvc ist weniger erprobt als mingw.
